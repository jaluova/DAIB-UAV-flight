# 工程适配与算法边界说明

日期：2026-08-09

## 文档目的

本文作为项目总结的补充材料，说明我们在现有算法基础上完成的工程适配工作，以及
后续代码协作需要共同遵守的算法边界。

当前阶段以项目主仓库中的算法实现、ROS 接口和坐标系约定为协作基线。接口名称、消息
类型和坐标关系暂不由工程适配侧重新设计；后续确有系统集成需要时，再由我们共同
讨论和调整。

现阶段最重要的对齐原则是：

> 工程兼容工作可以调整构建环境、依赖、设备配置、启动方式和部署工具，但不改变
> 定位、探索和规划模块的核心计算算法。

## 共同算法基线

项目继续以当前主仓库中的三个算法模块为主体：

- DAIB-LIVO 负责 LiDAR-Inertial-Visual 定位建图、退化感知、视觉记忆、PVBSM
  和回环相关计算；
- DAIB-Explorer 负责占据地图、frontier 提取、探索记忆、候选评价和目标选择；
- DAIB-Planner 负责目标接入、碰撞检查、局部重规划和 B-spline 轨迹生成。

工程适配不替换以上模块，也不修改其核心计算目标、代价函数、状态更新、候选筛选
和地图更新逻辑。现有算法特点和创新点以项目总结中的共同表述为准。

## 已完成的工程适配

在不改变核心算法定位的前提下，我们完成了面向 ARM64 实机的运行环境和传感器适配。
目标平台为 Orange Pi 5 Max（RK3588），算法和传感器驱动运行在 openEuler 24.03
LTS + ROS Noetic 容器中。

主要工作包括：

- Apple Silicon 到 `linux/arm64` 的镜像构建和 RK3588 部署流程；
- openEuler ROS Noetic 依赖安装、catkin 命令兼容和 OpenMP 链接处理；
- Livox MID-70 与 Intel RealSense D435i 的驱动容器和设备访问配置；
- LiDAR、相机和 IMU 话题接入及启动顺序整理；
- LiDAR-IMU、LiDAR-Camera 外参配置和独立投影检查；
- 传感器频率、时间戳、最近邻时间差和 rosbag 输入完整性检查；
- 算法容器与驱动容器之间的 ROS1 通信、数据目录和离线部署流程。

这些工作解决的是算法在目标硬件上能否构建、启动、接收正确输入和稳定运行的问题。
传感器外参、时间偏移和驱动参数会影响计算结果，因此必须经过实测确认，但它们不构成
新的定位、探索或规划算法。

## 接口与坐标约定

当前不重新定义系统接口和坐标系，直接沿用项目主仓库中的现有约定。按照当前代码，
SLAM odom 仍作为定位主状态，探索和规划模块继续消费主仓库已经定义的 ROS1 接口。

当前协作基线中的主要接口包括：

| 发布方 | 话题 | 类型 | 当前用途 |
|---|---|---|---|
| DAIB-LIVO | `/daib_slam/odom` | `nav_msgs/Odometry` | SLAM 定位主状态 |
| DAIB-LIVO | `/daib_slam/planning_cloud` | `sensor_msgs/PointCloud2` | 探索与规划环境输入 |
| DAIB-LIVO | `/daib_slam/degenerate` | `std_msgs/Bool` | 几何退化状态 |
| DAIB-LIVO | `/daib_slam/degeneracy_score` | `std_msgs/Float64` | 退化程度 |
| DAIB-LIVO | `/daib_slam/lio_runtime_ms` | `std_msgs/Float64` | 运行负载观测 |
| DAIB-LIVO | `/daib_slam/pvbsm_delta` | `sensor_msgs/PointCloud2` | PVBSM 增量 |
| DAIB-Explorer | `/daib_explorer/goal` | `geometry_msgs/PoseStamped` | 任务级探索目标 |
| DAIB-Explorer | `/daib_explorer/generation` | `std_msgs/UInt64` | 目标代次 |
| DAIB-Explorer | `/daib_explorer/ready` | `std_msgs/Bool` | Explorer 就绪状态 |
| DAIB-Explorer | `/daib_explorer/planning_cloud` | `sensor_msgs/PointCloud2` | 占据环境输出 |
| DAIB-Planner | `/daib_ego/position_cmd` | `quadrotor_msgs/PositionCommand` | 规划轨迹输出 |

上述表格记录的是当前协作基线，不表示接口已经永久冻结。如果后续更换整机平台、飞控
或控制器，我们优先在算法模块之外增加适配层，不直接改变 SLAM、Explorer 和 Planner
内部计算。飞控侧只需要接收定义清楚的轨迹或运动指令接口；具体平台可以在后续确定，
包括大疆或其他飞控方案。

坐标系和时间戳同样先沿用项目主仓库的现有实现。后续如需统一机体坐标、地图坐标或
控制坐标，应作为单独的系统接口设计任务共同讨论，不能在兼容代码中通过修改
`frame_id` 或时间戳临时绕过。

## 核心算法不变的具体范围

为了避免“兼容性修复”无意中改变算法，以下内容应视为核心计算边界。

### DAIB-LIVO

兼容工作不应改变：

- LIO/VIO 状态传播、观测更新和迭代求解；
- 退化指标及其阈值逻辑；
- 视觉帧选择和 CEM 视觉记忆策略；
- PVBSM 构建、筛选、保留和发布逻辑；
- 回环检测、约束构造和位姿图优化。

允许独立调整的内容包括编译选项、依赖查找、设备话题、最终确认的传感器参数、
launch、驱动容器和只读诊断工具。

### DAIB-Explorer

兼容工作不应改变：

- 占据状态更新和 frontier 提取；
- PVBSM 记忆和覆盖度计算；
- 候选目标生成、评分、切换和回环逃逸策略；
- 退化感知与动态计算预算。

本地做过的聚类安全视点、路径已知自由比例、围栏和目标保持实验属于算法改进，后续
是否采用需要单独讨论和 A/B 验证，不进入当前兼容基线。

### DAIB-Planner

兼容工作不应改变：

- EGO 地图参与碰撞判断的方式；
- B-spline 初始化、优化目标和可行性检查；
- 重规划状态机和轨迹刷新条件；
- 目标接受、失败恢复和轨迹输出的核心语义。

本地 observation-aware map、额外安全锁止和规划输入切换属于系统或算法行为修改，
后续是否采用需要单独评审，不进入当前兼容基线。

## 后续代码对齐方法

如果需要把工程兼容代码合入项目主仓库，建议始终从最新主线建立小范围修改，
而不是直接合并当前本地分支。每项修改保持单一目的：

1. ARM64、OpenMP 和依赖兼容；
2. MID-70/D435i 最终硬件配置；
3. 传感器检查和诊断工具；
4. 容器构建与部署文档；
5. 后续共同确认的飞控适配接口。

兼容性修改应尽量集中在构建文件、配置、launch、工具和部署目录。确实需要修改核心
`src/` 文件时，应先说明原代码为什么无法构建或接入设备，并证明修改没有改变计算
分支、默认参数和算法输出语义。

## 对齐验证

后续每次兼容代码对齐至少检查：

- 项目主仓库原有数据集、仿真和默认 launch 行为不变；
- 核心算法配置和默认阈值没有被兼容配置覆盖；
- 相同输入下，关键 odom、退化状态、目标和轨迹输出保持原有语义；
- ARM64 Release 构建以及启用测试的构建均能通过；
- 新硬件配置使用独立入口，不改变已有设备和数据集配置；
- 每次提交明确记录基线 commit、修改目的、验证方式和未验证项。

算法改进应与兼容性修改分开验证。算法改进需要固定 rosbag 或相同仿真场景下的 A/B
结果；兼容性修改主要证明既有算法在新环境中的行为保持一致。

## 仍需共同确认的内容

以下内容暂不在本文中定死，后续可以结合整机和演示目标共同调整：

- 最终对外暴露的话题名称和消息定义；
- SLAM、任务地图、机体和控制侧的坐标关系；
- 规划轨迹到具体飞控平台的适配接口；
- MID-70/D435i 最终外参、时间偏移和相机参与策略；
- 本地 Explorer 和 observation-aware map 改进是否进入主算法；
- 项目总结中采用的实验指标、对比基线和最终演示流程。

在这些内容确认前，我们保持项目主仓库接口和坐标约定不变，以 SLAM odom 作为定位
主状态，并把平台兼容逻辑限制在算法模块之外。

## 项目总结建议表述

> 在算法模块基本定型后，我们进一步完成了 ARM64/openEuler/ROS Noetic 工程适配，
> 建立了面向 Orange Pi 5 Max 的算法与传感器容器环境，并完成 Livox MID-70、
> Intel RealSense D435i 的驱动接入、外参管理、时间检查和 rosbag 验证流程。
> 工程适配沿用现有 SLAM、探索和规划接口，不改变三个模块的核心计算算法，主要解决
> 既有算法在目标硬件和传感器环境下的可构建、可启动、可观测和可复现问题。
>
> 当前系统继续使用 SLAM odom 作为定位主状态，探索和规划模块按照既有 ROS1 接口
> 解耦运行。飞控平台不绑定到算法内部，后续通过独立适配层接收规划轨迹或运动指令，
> 从而支持大疆或其他整机平台。接口名称、坐标关系和具体控制接入方式将在后续整机
> 集成阶段共同确认。
